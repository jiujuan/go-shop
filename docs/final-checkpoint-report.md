## 5. 修复的问题总结

### 5.1 统计系统属性测试修复 ✅

#### 问题描述
3 个统计系统属性测试失败：
- 属性 37: 商品销售排行正确性
- 属性 38: 订单状态分布统计正确性
- 属性 39: 收入统计计算正确性

#### 根本原因分析

1. **测试代码问题**: 属性测试使用 `suite.orderRepo.Create()` 创建订单，但该方法要求订单必须包含订单项（`order.Items`）。测试代码在创建订单后才单独创建订单项，导致订单创建失败。

2. **实现问题**: 
   - `GetSalesOverview` 方法在获取订单状态分布和收入统计时，没有按日期范围过滤，导致统计了所有历史订单而不是指定时间范围内的订单。
   - `GetProductSalesRanking` 方法的 SQL 查询缺少 `COALESCE` 处理 NULL 值，并且排序时没有添加次要排序条件。

#### 修复方案

**1. 修复测试代码** (test/property/statistics_property_test.go):
- 将 `suite.orderRepo.Create(suite.ctx, order)` 改为 `suite.db.Create(order).Error`
- 这样可以直接创建订单而不需要预先填充 `order.Items`
- 影响的测试：Property 37, 38, 39

**2. 修复 Repository 实现** (internal/repository/statistics_repo_impl.go):
- 添加 `GetOrderCountByStatusAndDateRange` 方法：按状态和日期范围统计订单数量
- 添加 `GetRevenueByDateRange` 方法：按日期范围统计收入
- 添加 `GetRefundAmountByDateRange` 方法：按日期范围统计退款金额
- 修复 `GetProductSalesRanking` 的 SQL 查询：
  - 使用 `COALESCE` 处理 NULL 值
  - 添加 `oi.product_id ASC` 作为次要排序条件

**3. 修复 Service 实现** (internal/service/statistics_service_impl.go):
- 修改 `GetSalesOverview` 方法：
  - 使用 `GetRevenueByDateRange` 替代 `GetTotalRevenue`
  - 使用 `GetRefundAmountByDateRange` 替代 `GetTotalRefundAmount`
  - 使用 `GetOrderCountByStatusAndDateRange` 替代 `GetOrderCountByStatus`

**4. 更新 Repository 接口** (internal/repository/statistics_repo.go):
- 添加新方法签名到接口定义

#### 修复结果

✅ 所有 3 个统计系统属性测试现在通过 100 次迭代  
✅ 测试覆盖率从 93.75% 提升到 100%  
✅ 需求 10.3, 10.5, 10.6 完全满足  

#### 技术细节

**修复前的问题**:
```go
// 问题 1: 测试使用 orderRepo.Create 但没有提供 order.Items
err := suite.orderRepo.Create(suite.ctx, order)  // 失败：order must have at least one item

// 问题 2: 统计方法没有按日期范围过滤
totalRevenue, err := s.statsRepo.GetTotalRevenue(ctx)  // 统计所有历史数据
```

**修复后的代码**:
```go
// 修复 1: 直接使用 DB 创建订单
err := suite.db.Create(order).Error  // 成功：绕过验证

// 修复 2: 按日期范围统计
```
